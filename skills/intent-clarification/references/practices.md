# 需求澄清机制：解释与实践依据

本文件随 Skill 独立分发，包含理解和执行规则所需的解释、案例及来源，不依赖仓库中的其他文件。遇到取舍、异常或适用边界不清时，按问题阅读相应部分。

## 规则逐条解释

### R1 先调查，后提问

优先查看已有对话、仓库、项目文档和可访问的环境信息，不让用户重复提供自己能够查明的事实。

把“事实在哪里”留给调查，把“用户希望怎样”留给决策。找不到资料时说明缺口，不把猜测补成事实。

### R2 只问关键歧义

不同解释会实质改变目标、范围、体验、风险或验收结果时，先澄清再执行。

判断问题是否关键，要看答错后的代价，而不是未填写字段的数量。

### R3 提问帮助决策

简短解释问题的影响；有真实取舍时给出少量具体选项、差异和建议，优先处理最关键的一项。

用户无需代替 Agent 做技术调查。选项应让用户看懂结果差异，避免堆砌内部实现术语。

### R4 明确退出条件

简单明确任务直接执行；低影响且可逆的不确定性可说明假设后推进；信息足以可靠执行时停止澄清。

合理假设不能覆盖破坏性、不可逆或超出授权范围的操作。

## 核心判断

澄清的价值由减少的误解和返工决定。先把可查事实与用户偏好分开，再按答错后的影响选择问题；当目标、必要约束和执行路径足够清楚时，及时退出澄清。

## 场景示例

例如，用户要求在已有播放器中加入倍速功能。现有倍速接口、组件位置和项目约定应先读取；是否需要跨设备同步倍速偏好，则可能需要用户决定。问题应解释两种行为的体验差异，并给出建议。若已有产品规范明确行为，就不再询问。此例体现的是事实调查、关键决策与退出澄清的分工。

## 适用边界与误用

### 实际使用中的观察方式

可以用明确小修改、仓库可查事实、高影响功能歧义和低风险缺失信息四类场景观察规则是否合适。分别关注是否直接执行、是否先调查、是否帮助关键决策，以及是否在说明合理假设后推进。反馈可包括无效提问、关键误解、返工、阅读和回复负担、验收结果、时间与词元成本。观察默认行为后优先保留有实际作用的最小规范；这些维度不代表本项目已经开展实验。

- 不用 AGENTS.md/Skill 承担推理正确性、工具可靠性等底层能力责任。
- 不将澄清设计为所有任务必须经过的冗长问答流程。
- 不强制用户决定 Agent 本可通过环境调查处理的普通技术细节。
- 不把社区项目的规则数量、Star 数或某次案例当作普适有效性的证据。
- 规则文本和格式检查不能证明行为增益。
