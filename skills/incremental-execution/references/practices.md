# 任务规模与执行节奏：解释与实践依据

本文件随 Skill 独立分发，包含理解和执行规则所需的解释、案例及来源，不依赖仓库中的其他文件。遇到取舍、异常或适用边界不清时，按问题阅读相应部分。

## 规则逐条解释

### E1 按可验证成果拆分

以可独立验证、值得独立审查的成果划分复杂任务，不按固定文件数、时间或工具次数拆分。

配置、准备和文档可以并入所支持的成果；科研可用证据表、推导或复现实验验收。

### E2 阶段验证失败先处理

必要阶段验收未满足时先修复或明确阻碍，不把问题悄悄带入后续阶段。

验证针对成果，检查强度与风险相称；不要求每个工具动作后运行全量测试。

### E3 区分通知、决策与权限

进度通知不要求用户回复；已授权范围内连续推进；重要目标变化和高风险副作用按实际授权处理。

让用户知道进展与让用户作决定是两回事。文本偏好不扩大平台权限。

### E4 无效尝试时重审路线

重复行动没有新证据时重新检查假设、诊断路线与方案，避免机械重试。

真实运行中的进程可以有效等待；困难探索可能反复失败但持续带来新信息，不按固定次数认定卡住。

### E5 受阻时留下恢复条件

确实缺失决定、权限、资料或可辩护路径时，说明阻碍、已完成工作、现有证据和恢复所需条件。

受阻报告要让接手者知道从哪里继续，不能用空泛的“稍后再试”或成功措辞掩盖未完成项。

## 研究问题与实践分析

### Q1：任务按什么依据拆分？

**共识**：以具有清楚边界、可以独立验证的成果划分任务，优先按用户可感知的功能或可独立审查的交付物组织；不要把“读取文件”“创建文件”“运行一次命令”机械等同于需要交付的独立任务。准备、配置、文档等工作可以纳入其支持的交付单元。

对复杂任务采用简短阶段计划并定义可观察的验收条件。对于简单明确的操作，不要求冗长计划。测试不是唯一验证手段：科研任务可以用证据表、复现实验或可核查推导来验收。

**依据**：OpenAI Codex 长任务案例采用 milestone + acceptance criteria + verification；Superpowers 的 writing-plans 明确将 task 定义为可独立测试、值得独立审查的最小交付单元。

### Q2：何时汇报，何时需要用户批准？

**共识**：区分三类不同交互：

- **进度通知**：简短说明当前成果、状态、风险，不要求用户每次回复。
- **决策确认**：目标、范围、关键取舍或验收预期发生实质变化，需要用户判断时暂停确认。
- **操作授权**：删除、外部发布、敏感权限、不可逆副作用等，按运行框架权限和用户明确授权执行；文本规范不是权限控制替代品。

在用户已授权的任务范围内，让 Agent 连续执行常规实现、必要验证和修复；不要把自动化检查转嫁成每步人工批准。汇报与批准不应混同。

**依据**：Superpowers subagent-driven-development 明确实行连续执行并列出需要暂停的风险边界；Codex 提供权限、沙箱等控制；Codex 长任务实践强调在里程碑层面引导而不是逐行微管理。

**注意**：Superpowers 部分版本对“歧义是否必须询问用户”的处理较激进；本项目仍以专题 01 的需求澄清共识为上位约束，不照搬“任何歧义都自行裁决”。

### Q3：何时暂停、调整方案或停止无效执行？

**共识**：不能只根据失败次数判定 Agent 卡住。应区分：

- **有效进展**：产生实质变更，或获取改变下一步判断的新证据。
- **有效等待**：已经确认有真实运行中的进程、任务或外部依赖，轮询有明确对象。
- **持续无效尝试**：重复行动得到相同结果，或仅改写叙述但没有新信息，应重新检查假设、诊断路线或方案。
- **真正受阻**：缺失用户决策、权限、资料或不存在可辩护的下一步，应说明阻碍、已完成部分及恢复所需条件，而非继续空转或虚报成功。

困难任务允许多轮探索；失败不等于没有进展。自然语言规则主要提醒 Agent 在无效推进时改变行为；自动循环识别和停止执行应优先依赖运行框架实现。

**依据**：OpenHands StuckDetector 检测重复动作-结果、重复错误和交替循环等；Codex Goal continuation 模板区别 progress、verified wait、no progress，并要求基于当前证据判断完成或受阻。

## 核心判断

小步执行控制的是未经验证便扩大的工作范围。阶段可以独立验收，普通实现可连续推进；出现无新证据的重复时重审假设，真正受阻时留下可恢复条件。

## 场景示例

例如，播放器倍速功能可以以“选择倍速后实际播放速度正确，切换资源后的行为符合需求”为一个交付单元。样式、状态与播放接口共同服务该成果，无需分别请求批准。若测试发现切换资源后速度复位，应先修复该问题。若只是在等待已确认运行的构建，轮询属于有效等待；重复同一报错却没有新诊断则需要重审路线。

## 适用边界与误用

- 固定要求每次只修改 1–3 个文件或调用固定次数工具；
- 每完成一个函数、文件或子步骤就要求用户回复“继续”；
- 不论任务大小一律生成详细计划、运行全量检查或人工审批；
- 固定失败 3 次就强制认定卡住；
- 将进度通知误当作正式验收，或将回复简短误当作实际进展；
- 用自然语言规范冒充运行框架权限、沙箱和自动检测的替代实现。
