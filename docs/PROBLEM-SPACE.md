# 人机协作的问题空间

## 问题起点

用户能够描述希望得到的结果，却通常无法一次写出全部需求、实施路线和验收条件。Agent 能补全许多技术细节，但补全也可能偏离用户意图。任务越复杂，目标、执行、解释、证据和记忆之间的偏差越容易累积，最后变成返工与监督负担。

本项目从这些反复出现的协作失效出发，围绕五个可区分的研究方向形成原则。研究对象包括开发、科研和一般复杂任务，其共同点是需要在不完全信息中持续取得可核查成果。

## 五类问题与因果链

### 需求澄清

直接猜测关键偏好可能做错方向，逐项追问又可能让用户承担调查责任。因此需要区分可查事实、用户意图和可逆假设。规则关注先调查、只问关键歧义、帮助决策和及时结束澄清。

### 任务规模与执行节奏

一次执行跨度过大，会让尚未验证的假设影响更多工作；拆得过细，又会增加计划和确认成本。小步执行的关键是形成独立可验收的成果，同时让常规实现连续推进。有效等待、带来新证据的失败和机械重复必须分别判断。

### 自然语言沟通与信息表达

术语和缩写可能遮蔽具体影响，极短回复可能缺少逻辑，大量过程汇报又会挤占用户注意力。解释深度取决于读者在相关领域的知识广度和深度。自然表达需要直接说明事实、作用与原因，并提供理解后续内容所必需的概念。

### 完成状态与证据表达

代码变化、测试通过、原问题解决和整体任务完成分别需要依据。证据还可能因版本、环境或后续修改而失效。复杂任务中的独立审查提供额外视角，但审查者也会误报，因此需要根据原始需求审查，再核实反馈。

### 长任务状态与恢复

压缩、换会话或跨日工作可能导致约束遗失、重复劳动和误用旧进度。记录必须包含任务身份和可定位产物，恢复时还需与真实文件、版本或实验结果核对。状态异常只触发检查，不能凭失败次数断定模型退化。

## 各专题怎样连接

需求澄清确定做什么和关键边界；执行节奏把目标转换为可验证成果；沟通让用户理解结果；证据决定可以作出多强的声明；状态管理让上述信息在长任务中持续有效。

这些职责存在交点。遇到新的关键歧义，应回到澄清；验证失败，应先修复或说明阻碍；进度通知不用等待审批；换会话后即使有完成摘要，也需要检查实际产物。

## 范围与目标

本仓库提供问题分析、30 条候选经验及其 Skill 实现。预期改善是减少关键误解、无效交互、返工和恢复成本。专门基准实验、模型能力评测和新运行框架不在项目范围内。

任务越简单，需要的结构越少。一个明确的文字修改可以直接执行，一次生产数据迁移则需要更完整的授权与验收。规则的使用强度应由复杂度、影响和交接风险决定。
