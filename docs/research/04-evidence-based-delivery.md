# 完成状态与证据表达

本报告围绕协作失效、公开实践、规则含义与适用边界展开。规则依据专题共识保留原始编号和语义，工程经验未在本项目中开展专门对照实验。

## 1. 问题与背景

本专题关注：Agent 可能尚未完成任务便宣称完成；未运行测试却声称通过；测试结果不能证明原始目标；改动破坏其他功能；最终汇报缺少可核查的证据。独立审查的设计要求是：**复杂任务完成后，可由主 Agent 派出具有独立上下文的子 Agent 审查，降低主 Agent 沿用原先假设、忽略问题的风险。**

**专题目标**：让 Agent 的完成声明严格对应真实状态与有效证据；对复杂、重要或反复失败的任务，通过按需独立审查补充验证视角；向用户以可理解、低负担的方式呈现结果。

此专题要解决“结论能否被工作证据支持”。说话方式本身由专题 03 负责；执行阶段控制由专题 02 负责。

## 2. 研究问题

怎样判断真实完成状态？哪些证据能够证明原始目标？如何低负担地呈现证据？怎样安排和处理独立子 Agent 审查？

研究同时关注规则能带来的增量，以及规则可能增加的询问、阅读、执行和维护成本。语言模型与运行框架承担推理、工具和权限等基础能力；文本规范只补充协作选择与工作习惯。

## 3. 相关实践与问题分析

### Q1：如何准确判断任务完成状态？

**结论：完成状态必须针对已约定的任务范围；“产生修改”“测试通过”“原始问题解决”“整体交付完成”不是同一项事实。**

| 状态 | 事实基础 | 对用户可说的话 |
|---|---|---|
| 已实施，待验证 | 已产生代码或其他交付物，缺少充分检查 | “已实现相应修改，实际效果尚未验证。” |
| 部分完成 | 部分验收条件满足，其余未完成 | “A、B 已完成，C 仍需处理。” |
| 验证失败 | 运行过验证，结果不满足条件 | “修改已完成，但相关测试仍有失败。” |
| 已验证完成 | 在所述范围内满足验收标准，有对应证据 | “该项功能已完成，约定的检查均已通过。” |
| 受阻 | 权限、环境、必要信息或可行路径不足 | “目前受 X 阻碍；恢复需要 Y。” |

这些状态是沟通时使用的概念模型，不要求每个 Agent 创建专门的状态机，也不要求每次汇报都生成状态表。

### Q2：什么证据能支撑完成声明？

**结论：证据必须检验当前交付物与原始目标，且没有被后续修改失效。**

- Bug 修复：优先证明原始问题已复现并在修改后得到解决，辅以相关回归检查；仅编译通过不足以证明问题修复。
- 功能开发：对照验收场景检查用户可见的完整路径；单个函数的单元测试不能替代必要的端到端或集成验证。
- 重构：检查关键行为、接口兼容性和回归测试；“能够启动”不代表行为没有变化。
- 性能优化：在可比较的条件下测量，不能只依据代码结构推断加速。
- 科研分析：核对数据、计算、实验记录或文献证据，不把局部结果描述为已验证的普遍结论。
- 文档分析：核查需求覆盖、引用来源、事实与原材料的对应关系。

“新鲜证据”指证据仍然适用于**当前版本和当前范围**，并不要求每次回复都机械重复执行所有测试。当后续修改可能影响既有结论时，重新进行相关检查。

**证据来源也重要**：运行日志或测试输出可能被截断、来自错误的工作区、指向旧版本，或只是第三方报告。Agent 应优先核实产物、执行对象、退出状态和关键结果，而不是看到“pass”字样便视为成功。

### Q3：如何让用户容易理解完成与验证结果？

**结论：报告以“实际结果—必要证据—重要遗留”为核心，详细日志按需提供。**

简单任务示例（前提是确已执行相应检查）：

> 已修复拖动进度条后播放位置跳回的问题。相关测试已通过。

复杂任务示例：

> 已完成播放器状态管理重构；相关单元与集成测试均通过。低性能设备上的实际播放表现尚未验证。

受阻任务示例：

> 已实现修复并完成本地检查，但无法连接目标测试环境，暂时不能确认线上部署结果。需要可用的测试环境后继续。

**禁止虚构命令执行、测试通过、子 Agent 审查完成或用户已经批准等事项。** “未验证”是一种正当状态，不需要用长篇防御性说明掩饰。

### Q4：如何使用独立子 Agent 审查？

**结论：在复杂、高风险或多次受阻的任务中，优先考虑由独立上下文的审查 Agent 核对原始需求、实际交付物和验证证据；主 Agent 最终核实审查发现。**

成熟做法：

1. **Anthropic 代码审查插件**：对 PR 派遣多个审查 Agent，分别关注规则遵守、代码缺陷、提交历史等，使用置信度筛选降低低价值反馈（参见来源 4）。这证明了独立、分工的审查在工程工具中具有可行性。
2. **Superpowers 请求代码审查**：审查 Agent 接收经过整理的需求、变更范围与代码证据，**不继承主 Agent 的完整会话历史**；在主要功能完成、合并前、复杂 Bug 或工作受阻时使用（来源 2）。
3. **Superpowers 处理代码审查意见**：收到审查意见后，先依据项目现实核实，再决定是否修改；独立审查意见并非天然正确（来源 3）。
4. **OpenAI 运行框架工程**：通过自动化测试、应用使用反馈及多 Agent 工程流程补充人工难以持续提供的质量反馈（来源 5）。

**审查输入建议**：原始任务/验收标准、项目必须遵守的约束、当前实际变更（例如 Diff、产物或数据）、相关验证结果、需要检查的风险点。可以提供必要的项目背景，但不要让主 Agent 的“我已经解决问题”结论替代原始要求。

**审查重点**：需求是否覆盖、代码或分析是否存在可复现问题、既有证据是否足够、是否引入范围外副作用、是否存在遗漏的关键边界条件。

**审查后处理**：要求子 Agent 给出可定位、可复核的问题与依据；主 Agent 对重要发现进行技术核查，有理有据地接受或反驳；修复后重新验证受影响部分。独立的上下文减少共用假设的风险，**不保证独立审查一定正确**；同类模型仍可能犯相似错误。

**触发边界**：简单文字、低风险配置和很小的修复通常只需主 Agent 做相关检查；架构改动、跨模块功能、并发/安全/数据完整性问题、复杂或反复失败的调试更适合考虑独立审查。如果运行框架不支持子 Agent，则保留人工审查或独立的第二遍检查作为降级路径，但不能宣称已经进行子 Agent 审查。

## 4. 核心发现

完成声明必须对应当前产物和原始验收目标。独立审查补充视角，其输入应保留原始需求，输出仍需要主 Agent 核实，形成“验证—独立判断—核查反馈—必要修复与再验证”的闭环。

公开工作流证明这些做法存在且能够被工程化组织，不能单独证明其对所有 Agent 都有效。采用时应结合任务规模、默认行为和平台能力，保留有价值的约束，避免把特定项目的固定数量或工具命令推广成通用要求。

### 场景解释

例如，单元测试通过只能支持其覆盖的行为。用户要求解决低性能设备播放卡顿时，仍需要在可比较的设备和场景下观察或测量。审查 Agent 收到原始症状、变更和测量结果后，应独立查找遗漏；主 Agent 要复核其发现，不因“独立审查”四个字就接受未经定位的结论。

## 5. 协作原则与执行含义

### V1 准确区分完成状态

明确区分已实施待验证、部分完成、验证失败、已验证完成和受阻，让声明符合真实范围。

无需固定输出状态表；不能用“改了代码”替代“已验证修复”。

### V2 关键声明由相关证据支持

对照原始用户目标选择检查，对实际交付物核查需求覆盖、行为和必要回归。

科研、性能、文档与软件任务需要不同证据，不强制同一种测试。

### V3 保证证据对当前产物有效

核对工作区、版本、环境、执行对象和输出；后续修改影响旧结论时重新检查相关部分。

新鲜指仍适用，不要求每次回复或无关微改后重跑全量测试。

### V4 简洁报告结果与必要证据

先讲实际结果，再给必要证据和重要遗留，详细日志按需提供。

不得虚构执行、测试、审查或审批；具体未验证范围直接说明。

### V5 按需使用独立审查

复杂、高风险或反复受阻任务考虑独立上下文的子 Agent 审查，结合平台能力与成本选择。

简单微任务不强制派审查者；工具不可用时如实采用人工或独立第二遍检查。

### V6 审查基于原始需求和交付物

给审查者原始任务、验收标准、约束、实际变更和相关证据，让其独立判断。

提供必要事实，不用主 Agent 的主观成功结论或完整思路替代原始材料。

### V7 核实审查意见后再修改

要求发现可定位、可复核；依据代码、数据或实验核查，决定接受或反驳，修复后验证受影响部分。

独立上下文不保证正确。审查误报和相似模型的共同盲点都需要考虑。

## 6. 适用边界

- **验证不等于穷尽证明**：成功说明特定检查及其覆盖范围，不能无限扩展为“系统没有任何问题”。
- **审查 Agent 不等于更权威的 Agent**：从不同上下文重看事实可能减少沿用主 Agent 错误假设，但也可能误报。语言模型 代码评审存在将正确实现判断为不合规的实证风险（来源 6）。
- **验证的时间和对象必须可对应**：错误的环境、旧提交、截断的日志或不可信输出可能使表面“通过”失效（可参考来源 7 的社区讨论）。
- **不要把审查变成流程负担**：不对所有简单改动强制多 Agent 审查，不因为形式上的“有审查”忽略真正测试。
- **工具权限不是文本规则可以替代的**：对子 Agent 审查或代码合并等操作，遵循运行框架实际权限与审批要求。

这些原则与其他专题共同作用时，关键目标歧义优先澄清，授权内的常规工作连续推进；表达简洁仍保留必要证据；持续无效失败先重审路线，跨会话则核对状态。各专题有独立职责，不要求按固定顺序全部加载。
