# 长任务状态管理与上下文恢复

本报告围绕协作失效、公开实践、规则含义与适用边界展开。规则依据专题共识保留原始编号和语义，工程经验未在本项目中开展专门对照实验。

## 1. 问题与背景

本专题关注：长会话中遗忘早期约束、重复已完成的工作、上下文压缩遗漏关键决策、错误假设持续累积、无法及时发现任务推进质量下降，以及切换会话后难以恢复真实进度。

**专题目标**：让长期任务的重要状态不依赖单次对话历史保存；出现行为异常时先核查任务和实际产物；根据工作状态选择继续、压缩、开新会话或独立子 Agent；在跨会话恢复时避免重复工作和误用过期状态。

本专题的关注点是“如何维持与恢复工作状态”。执行节奏由专题 02 负责，完成声明的真实性由专题 04 负责。

## 2. 研究问题

如何发现工作状态可能退化？哪些事实需要持久化，如何验证记录？什么时候继续、压缩、换会话或隔离子任务？

研究同时关注规则能带来的增量，以及规则可能增加的询问、阅读、执行和维护成本。语言模型与运行框架承担推理、工具和权限等基础能力；文本规范只补充协作选择与工作习惯。

## 3. 相关实践与问题分析

### Q1：如何识别自身工作状态可能退化？

**结论：以可观察的行为异常作为检查触发信号，通过实际任务材料核查原因，不根据上下文长度或失败次数直接断言模型“变笨”。**

| 信号 | 可观察表现 | 正确的下一步 |
|---|---|---|
| S1：遗忘约束 | 已经明确的接口、架构或禁改范围被忽视 | 读取最新约束与相关决定，核实当前修改 |
| S2：重复劳动 | 已完成的任务再次实施 | 比对进度记录、文件与 Git 提交 |
| S3：判断矛盾 | 方案与已达成的决定冲突，却没有新证据 | 核对决策依据，明确变化来源 |
| S4：无效循环 | 反复相同操作或失败，不能提供新信息 | 重新检查根因和下一步的有效性 |
| S5：纠偏无效 | 多次纠正相同误解，仍反复出现 | 重建目标及约束，考虑清理或新会话 |
| S6：压缩后异常 | 压缩后遗漏关键任务、文件和决策 | 检查持久化状态；必要时交接并新建会话 |

这些信号**只能提示风险**。复杂 调试 可能自然包含多次失败；新的实验事实也可能合理推翻旧判断。核查后能解释的变化不必被误判为退化。

**实践依据**：Claude Code 官方最佳实践讨论了长上下文导致指令遗忘及更多错误；Cline 问题报告5790 报告了自动压缩后重新执行已经完成的任务。OpenHands 的 StuckDetector 则说明部分重复循环可以在运行框架层识别（见来源 1、5、6）。

### Q2：如何可靠保存与恢复长期任务状态？

**结论：持久化保存“恢复工作所必需的事实”，而非完整对话；恢复时以当前项目/文件/版本为准核对记录。**

建议的最小信息集：

| 信息 | 保存内容 | 目的 |
|---|---|---|
| 任务身份 | 项目、任务名称、计划/分支/工作区 | 防止不同任务状态串用 |
| 目标与边界 | 用户意图、验收标准、关键约束 | 防止目标漂移 |
| 完成进度 | 已完成、处理中、待完成及可定位产物 | 避免重复工作 |
| 重要决策 | 选定与放弃的方案及理由 | 防止无依据反复摇摆 |
| 验证与异常 | 已执行的检查、结果、失败原因 | 避免失效的成功声明 |
| 恢复入口 | 当前阻碍、下一步及所需资源 | 降低新会话恢复成本 |

**信息分层**：项目长期约束放在项目文档或少量全局规则；任务目标和实施计划放在任务文件；阶段进展、决策与证据放在动态状态记录；冗长日志留在原始文件/工具输出中，必要时检索，不长期占据提示词上下文。

**实践依据**：

- Cline 记忆库 使用 `projectbrief.md`、`activeContext.md`、`progress.md` 等文件记录项目基础信息、当前焦点与进度。我们借鉴其职责划分，不强制照搬全部文件。
- OpenAI 长任务 Codex 案例分别用 spec、plan、runbook 和动态文档维护目标、阶段验收、执行与决策。
- Superpowers 为每个计划维护专属 进度账本，并在恢复时对照实际 Git 提交。此前使用共享 进度账本 的设计曾导致不同计划错误复用进度，后改为按计划隔离的工作空间。

**恢复顺序建议**：先识别任务身份和当前工作区，再读取相关目标/约束/进度，核对 Git、文件、数据或测试结果，确认下一步后继续。记录与实际结果冲突时应先解决冲突，不把旧摘要视为唯一事实来源。

### Q3：何时继续、压缩、新建会话或派出子 Agent？

**结论：优先使用运行框架已有机制；依据任务连续性、是否存在上下文干扰、是否持续无效推进及工作是否可独立拆分选择方式。**

| 情形 | 首选方式 | 注意事项 |
|---|---|---|
| 当前任务正常推进、尚无状态异常 | 保持会话 | 避免无谓重建上下文 |
| 同一任务需要继续但历史信息冗余 | 使用原生压缩/清理 | 保留关键目标、约束、进度和当前证据；不要假设压缩绝不丢信息 |
| 当前任务已经结束，准备做无关新任务 | 开新会话 | 减少无关历史污染 |
| 多次纠偏仍无法稳定遵守关键约束 | 核查并持久化状态后，考虑新会话 | 不能仅凭一次错误机械切换 |
| 压缩后重复工作、遗漏任务或反复压缩却无进展 | 先恢复状态，必要时新会话交接 | 以真实产物核对摘要，防止继续传播错误 |
| 需要大量独立调查、文献阅读或代码检索 | 视运行框架能力使用子 Agent | 为子 Agent 提供任务范围与必要上下文，减少主上下文污染 |
| 数日/多会话的连续任务 | 使用持久化状态记录交接 | 新会话先验证记录适用性 |

**注意**：原生 上下文压缩 有时使用模型或平台的内部状态，不等同于可供人审阅的 Markdown 摘要。不要要求用户或 Skill 直接编辑平台返回的不可读压缩对象；跨会话的可读记录是独立的工作层。

**实践依据**：Claude Code 推荐利用压缩、清理、恢复和子 Agent 控制上下文；OpenAI Responses API 提供自动与显式压缩能力；Superpowers 把子 Agent 的输入限定为其实际任务和相关约束。

## 4. 核心发现

长期任务需要独立于对话历史、能够核查的关键状态。异常是检查触发信号；恢复应核对真实工作区和产物，再选择合适的上下文管理方式。

公开工作流证明这些做法存在且能够被工程化组织，不能单独证明其对所有 Agent 都有效。采用时应结合任务规模、默认行为和平台能力，保留有价值的约束，避免把特定项目的固定数量或工具命令推广成通用要求。

### 场景解释

例如，记录显示某分析阶段完成，但当前数据集已更换。恢复时应先确认任务身份、数据版本和结果文件，再判断旧结论是否适用。不能仅凭摘要中的“完成”跳过，也不能因换会话就重新跑完所有阶段。修正记录后，从首个确实未完成或已失效的成果继续。

## 5. 协作原则与执行含义

### M1 识别可疑状态退化

遗忘约束、重复工作、无依据矛盾或无效尝试时，先核对任务记录和真实状态。

任务困难、一次失败或上下文长度不能单独证明退化。

### M2 重要任务状态持久化

长任务保存身份、目标、约束、进度、关键决定、验证、异常与下一步。

粒度与交接风险相称，简单任务不强制建立完整记忆库。

### M3 恢复前核查真实状态

压缩或新会话后，先核对工作区、版本、文件、数据或实验结果，再继续。

记录与实际冲突时先查原因，防止误用旧计划而重复或跳过工作。

### M4 分开长期规范与临时状态

按生命周期分开项目约束、任务计划、动态进度与临时工具输出。

常驻规则和 Skill 不用作日志库，可重新获取的大量输出留在原处。

### M5 按状态选择上下文管理方式

正常推进则继续；同一任务历史冗余时按需压缩；无关任务用新会话；状态异常先核对。

优先使用平台原生机制，不假定能访问或编辑内部压缩对象。

### M6 避免无效压缩循环

反复压缩仍无法取得实质进展时，保存可靠交接信息并考虑新会话。

根据恢复效果判断，不设通用压缩次数或上下文比例阈值。

### M7 用子 Agent 隔离独立工作

资料量大或可隔离的子任务可使用独立上下文，提供边界与必要材料并简洁回传。

依赖平台支持和当前授权；控制成本，不能虚称派遣，也不能忽略返回结果核查。

## 6. 适用边界

- 不把“长上下文必然更差”作为确定性判断；模型、任务和历史内容都会影响表现。
- 不把“压缩”视为完全可靠的记忆恢复，也不要求所有任务必须压缩。
- 不把持久化任务记录误当成无需校验的事实；尤其防止错分支、旧计划和过期文件。
- 不让 Agent 每一步都向用户请求是否开新会话；正常推进时保持自治。
- 不要求 Skills 访问/改变不被运行框架暴露的内部上下文状态。
- 不以自然语言规则冒充工具层的循环检测、权限控制和真实的任务暂停能力。
- 如子 Agent 不可用，不虚称已经派遣；按当前运行框架能力选择只读检查或主 Agent 自查。

这些原则与其他专题共同作用时，关键目标歧义优先澄清，授权内的常规工作连续推进；表达简洁仍保留必要证据；持续无效失败先重审路线，跨会话则核对状态。各专题有独立职责，不要求按固定顺序全部加载。
